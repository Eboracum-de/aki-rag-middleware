# CLA acceptance process

SunaQ uses a Contributor License Agreement only for contributions where a clean dual-licensing rights chain matters. The goal is to keep routine community participation lightweight.

## No CLA required for

- bug reports and feature discussions;
- operational feedback;
- reproduction steps and logs after redaction;
- very small typo/formatting fixes that are not meaningfully copyrightable;
- links to public information.

## CLA required before merge for

- non-trivial source-code changes;
- substantial tests, prompts or documentation;
- contributed modules or features;
- other copyrightable work that the maintainer intends to include upstream.

## Individual contributors

Until a CLA automation is configured, the pull request must contain a comment from the contributor's GitHub account with the exact statement:

> I have read and agree to SunaQ CLA v1.0 (`CLA.md`) for the contributions in this pull request.

The maintainer records acceptance in the pull request before merge.

## Contributions owned by an organization

If an employer or other legal entity owns the contribution, an authorized representative of that entity must agree to CLA v1.0. Contact the maintainer in the pull request before merge; a separate signed/electronic confirmation may be requested.

## Why a CLA exists here

The public project is AGPL-3.0-only. Eboracum GmbH also wants to retain the option to conclude separate commercial license agreements when an organization needs different terms. A normal AGPL contribution is sufficient for AGPL distribution, but not necessarily for relicensing that contribution under a different commercial license.

The CLA therefore grants additional **non-exclusive** rights; it does not transfer the contributor's copyright. Accepted contributions remain available in the public upstream project under AGPL-3.0-only as described in `CLA.md`.
